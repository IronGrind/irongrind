IRONGRIND / ERD DEFENSE GUIDE 1 / 5

Before you trace the lines

Point to the whole Figure 5 first. Then use the attendance and members tables to introduce the labels.

“Figure 5 shows how IronGrind, our web-based gym management system, stores records across 13 public tables. Each box is a table. The fields inside it are columns, and each row in the database is one record, such as one gym visit.”
id and PK
Point to members.id. “A primary key uniquely identifies a row. This ID identifies one member, even if two members have the same name.”
FK and member_id
Point to attendance.member_id, then members.id. “A foreign key references a related record. This field holds the ID of the member whose visit was recorded.”
UQ and data types
Point to profiles.username and the type column. “UQ means the field has a uniqueness rule. The type tells us what kind of value it holds. A UUID is an identifier. A field such as username holds text.”
Other fields
Point to members.plan and attendance.time_in. “These fields describe the record. The plan tells us the member’s current plan, and time in tells us when the visit began.”
Line symbols
Point to the legend. “A solid line connects public tables. A dashed line connects to the managed Auth table. The crow’s foot shows the many side. A circle shows that a relationship end is optional.”

Transition “Now I’ll follow each connector separately, from the foreign key to the key it references.”

IRONGRIND / ERD DEFENSE GUIDE 3 / 5

Account and membership

Start at the first field. Follow that connector and stop at the second field before moving to the next item.

01

profiles.id → auth.users.id

“Connects the IronGrind profile to the user’s sign-in account. The profile stores application details such as the role.”

02

membership_applications.auth_user_id → auth.users.id

“Identifies the sign-in account associated with the application.”

03

membership_applications.reviewed_by → profiles.id

“Identifies the profile of the account that reviewed the application, when a reviewer is recorded.”

04

members.application_id → membership_applications.id

“Lets us find the original application associated with creating the member record.”

05

members.auth_user_id → auth.users.id

“Links the gym member record to a sign-in account when one is linked.”

06

membership_applications.member_id → members.id

“Identifies the member a request concerns. For example, a renewal request can refer to an existing member.”

07

membership_history.member_id → members.id

“Identifies whose membership changed. One member can have several history records.”

08

membership_history.recorded_by → auth.users.id

“Identifies the account that recorded the membership change, when that information is available.”
