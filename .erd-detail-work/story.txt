1|Figure 5: Reading the ERD
Welcome to IronGrind's Entity Relationship Diagram. Figure Five shows thirteen public application tables and the connections between their records.
A primary key uniquely identifies a row. A foreign key references a key in a related table.
In a one-to-many relationship, a single parent can be referenced by multiple child rows. The crow's foot marks the many side.
We will follow Ana from registration to renewal, a gym visit, and a purchase. Then we will see how an administrator saves a report and reviews the audit history.

40|Account and membership application
Ana submits her online registration. Supabase Auth manages her login identity. The profiles table holds her application account details, including username, email, and role.
The profile I D is both the primary key and a reference to Auth users. This ties the application profile to the same login identity.
One row in membership applications represents a registration, renewal, or plan-change request. Its I D identifies the request, and the status records its review outcome.
The Auth user I D points to the applicant's login identity. Reviewed by points to profiles, which identifies the reviewing account when recorded.

80|Approval and the member record
Once Ana's first registration is approved and a member row is created, members holds her current plan, start date, end date, and membership status.
The I D in members identifies Ana's gym member record. Its Auth user I D can link it to her login account.
The application I D in members references membership applications. Follow this link from the member record to find the application associated with its creation.

108|Renewal for an existing member
Later, Ana submits a renewal. The new request can use member I D in membership applications to reference her existing members record.
The two links answer different questions. Application I D points from a member to the original application. Member I D points from a request to the member it concerns.
The request keeps its own type and review status, so it can move through the review workflow separately from the current membership.

139|Membership history
To see Ana's current plan, look in members. To see a recorded change, such as a renewal or plan change, look in membership history.
Each history row represents one recorded membership event. Event type identifies what happened, and the row can include previous and new plan details.
Member I D in membership history references members. Ana can have several history records, all pointing to the same member I D.

166|Attendance records
Ana arrives at the gym. Her visit is recorded in attendance, including the date and check-in time. A check-out time is added when a check-out is recorded.
The member I D in attendance references the I D in members. This tells us whose visit it was.
If Ana visits again tomorrow, the visits have separate attendance identifiers and share her member I D. This is a one-to-many relationship.
Recorded by and checked out by can reference Auth users. Those links identify the account responsible for each action when recorded.

198|Mobile phone pairing policy
For phone-based scanning, mobile attendance pairing policy stores system-wide pairing settings, including the maximum number of paired phones.
The policy record describes how pairing is configured. Ana's actual check-in and check-out information is stored in attendance.

222|Mobile scan sessions and events
Mobile attendance scan sessions stores records for paired scanner sessions. Created by can be followed to Auth users to identify the account that created the session.
Mobile attendance scan events stores event records associated with a scanner session. Its session I D references the I D in mobile attendance scan sessions.
One session can have multiple event records. The event link identifies the scanner session, while member I D in attendance identifies the member who visited.

251|Products and inventory
After her visit, Ana buys one gym shirt and two units of a supplement. Each catalog product has its own record and I D in products.
The product record includes the item name, category, price, stock, and active status. The active status can control whether the item appears in the active catalog.
The sales workflow can use the product reference to update the stock of the item being sold.

274|Sales and line items
Sales stores one row for the entire checkout, including the total and receipt information. When the sale is linked to Ana, member I D references her members record.
Member I D is optional, which allows a sale to be recorded without linking it to a gym member. Processed by can link the sale to the responsible Auth account.
Sale items stores one row per line. Ana's shirt and supplement make two lines. The supplement line has quantity two.
Each line uses sale I D to reference the same sales record. Each merchandise or supplement line can use product I D to reference its own catalog product.
The line stores the item name, quantity, and unit price at the time of sale. This preserves the transaction details if the catalog changes.

313|Generated reports
An administrator chooses a report type and date period. For a sales report, the system can use sales transactions and their lines to prepare the summary.
When a report is saved, generated reports stores one report record with the report type, period, format, and report data.
Generated by references profiles dot I D. It identifies the account that generated the report. A single profile can be associated with multiple saved reports.

345|Activity logs
Activity logs stores recorded system events. The event can contain the action, time, actor details, and identifiers for the affected entity.
Those audit identifiers describe the event. The public diagram does not declare a foreign key from the activity log to the affected record.
Saving a generated report can write an audit event. The saved report describes the output, while the audit event records the action.

368|Recap: Following the keys
Ana's request is in membership applications. Her current membership is in members, and her recorded changes are in membership history.
Her visit belongs to her member record. Her checkout has two sale lines, and each line can point to a catalog product.
The saved report points to its creator's profile. Recorded actions can be reviewed in activity logs.
